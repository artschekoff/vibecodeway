# Основные циклы работы ИИ в приложении

## Понятийный аппарат

* **Контекст** — контейнер, в котором сохраняются все переписки участников команды по модулю (или теме):
  * Сообщения Slack
  * Тикеты и комментарии Jira
  * Репозитории с кодом, pull requests с комментариями

  Все эти сообщения так или иначе релевантны предметной области и рабочим процессам текущего модуля.

* **Модуль** — структурный объект рабочей системы, который выполняет определённую логическую задачу для нужд бизнеса. Модуль характеризуется предметной областью (какие сущности в нём взаимодействуют) и рабочими процессами (как эти сущности взаимодействуют). Например, система оплаты: сущность пользователя обращается к сущности товара, получает его цену и доступность, создаёт заказ, заказ передаётся на платёжный шлюз, шлюз проверяет поступление денег, формирует чек и закрывает заказ.

# Основные требования к ИИ

## Работа с требованиями

ИИ должен чётко разграничивать:

| Тип | Источник | Поведение ИИ |
|---|---|---|
| Официальное требование | Jira-тикет, формальный документ, прямое подтверждение | Воспринимать как аксиому, продолжать обработку |
| Неформальное упоминание / желание | Комментарий в Slack, предположение в переписке | Фиксировать как открытый вопрос, не влиять на план до подтверждения |
| Спорное (комментарий, не тикет) | Подтверждение вне Jira | Уточнить у пользователя: «это теперь официальная постановка?» |

Если в неформальных источниках есть информация, не учтённая официальной постановкой — взять во внимание при анализе и явно предупредить об этом.

## Открытые вопросы

* ИИ задаёт открытые вопросы, если встречает неоднозначность или неполноту требований.
* Пользователь отвечает на вопросы в чате — каждый ответ сохраняется как событие в event log типа `open_question_answered` и учитывается при следующем анализе.
* ИИ может рекомендовать, к кому обратиться за уточнением, исходя из авторства сообщений в источниках.

# Шаги работы агента

## Текущий шаг (Current Step)

Это новая сущность — отдельная от статуса (`workflow_status`). Хранится явно.

* ИИ идентифицирует предметную область и бизнес-требования, преобразует их в бизнес-сущности системы, анализирует рабочие процессы и определяет **текущий шаг** — что именно сейчас выполняется или должно выполняться.
* Агент анализирует прошлые важные изменения (event log), чтобы понять актуальное состояние задачи.
* Если агент неверно идентифицировал текущий шаг — пользователь может исправить это в чате. Исправление сохраняется как событие `current_step_override` и учитывается при последующих запусках.
* Структура:

```json
{
  "description": "Что именно сейчас делается",
  "identified_from": ["event-12", "event-34"],
  "confidence": "high | medium | low",
  "overridden_by_user": false
}
```

## Следующий шаг (Next Step)

* Обработать новый поток данных, идентифицировать сигнал среди шума, составить план изменений с учётом того, что уже сделано, что сделано неверно, что нужно с нуля.
* Сформировать задачу с упоминанием ключевых сущностей, рабочих процессов, требуемого результата, бизнес-логики, важных деталей.

# Критерии приёмки

Продуктом работы агента должен быть набор данных, который можно передать другому агенту-программисту так, чтобы тот понял, что именно нужно изменить, создать или проверить.

**Пример:** контекст посвящён insights MVP. В Jira-тикете: «реализовать GET API, возвращающий список всех сущностей» — это официальное требование. В Slack кто-то написал: «метод получения одного инсайта по id забыли сделать» — это открытый вопрос со ссылкой на автора. Если далее появляется подтверждение в чате — задача переходит в официальный статус, но если это было в комментарии, а не в тикете — агент уточняет.

# Момент вызова агента

**Анализ запускается вручную** — по нажатию кнопки «Analyze» внутри контекста. Фоновый рефетч данных (Jira/Slack/GitHub) и запуск анализа — два отдельных действия.

При первом запуске агент:
1. Извлекает события из всех источников (Jira, Slack, GitHub, загруженные файлы).
2. Задаёт вопрос: «Что уже реализовано по этому контексту?» — опциональный шаг; если ответа нет, работает от пустого `current_step`.
3. Строит snapshot и сохраняет event log.

При последующих запусках агент берёт предыдущий event log и snapshot как стартовую точку, обрабатывает только новые данные (дельта), обновляет snapshot.

**При вводе текста в чат** агент сохраняет ответ пользователя как событие в event log (тип определяется контекстом: `open_question_answered`, `user_note`, `current_step_override`) и вызывает `update_consolidated` для обновления snapshot.

# Sync Session — пакет изменений

Каждый запуск «Refresh All» (или индивидуальной синхронизации источника) создаёт **sync session** с уникальным `sync_session_id`. Все элементы, загруженные в рамках этого рефетча — Jira-тикеты, Slack-треды, GitHub PRs, коммиты — получают ссылку на этот `sync_session_id`.

Когда пользователь нажимает «Analyze», агент:
1. Определяет `last_analyzed_session_id` из предыдущего snapshot (или берёт первую сессию, если snapshot пуст).
2. Берёт все данные, привязанные к сессиям **после** `last_analyzed_session_id` — это и есть дельта для обработки.
3. Извлекает события только из этой дельты, дописывает их в event log.
4. Перестраивает snapshot из полного event log (включая новые события).
5. Сохраняет `last_analyzed_session_id = текущая сессия` в snapshot.

Это позволяет агенту:
- Не перечитывать весь исторический массив данных при каждом запуске.
- Чётко знать, какие изменения он уже учёл, а какие — нет.
- Обеспечить трассируемость: каждое событие в event log ссылается на `sync_session_id`, из которого оно было извлечено.

### Структура sync session

```json
{
  "sync_session_id": "sess-20260511-143022",
  "started_at": "2026-05-11T14:30:22Z",
  "finished_at": "2026-05-11T14:30:45Z",
  "sources": ["jira", "slack", "github"],
  "items_fetched": 42
}
```

### Обновлённая структура события в event log

```json
{
  "id": "event-441",
  "sync_session_id": "sess-20260511-143022",
  "type": "requirement_stated",
  "timestamp": "2026-05-10T14:23:00Z",
  "source_type": "jira | slack | github | chat | user",
  "source_id": "PROJ-123 | msg-abc | pr-88 | chat-msg-7",
  "author": "username или имя",
  "summary": "Краткое описание события (1–2 предложения)",
  "raw_reference": "Оригинальный текст или ссылка на исходный источник"
}
```

> **Примечание:** события из чата пользователя (`user_note`, `open_question_answered`, `current_step_override`) не привязаны к sync session — они создаются в момент отправки сообщения и имеют `sync_session_id: null`.

# Как хранить и что передавать

Агент работает с тремя уровнями хранения данных:

```
event log  →  snapshot (3 секции)  →  handoff packet
 (память)        (состояние)          (задача агенту)
```

Каждый уровень строится из предыдущего. Event log — первичен и append-only. Snapshot — проекция event log. Handoff packet — экспорт из engineering-секции snapshot.

---

## Event Log — память агента

Event log хранится append-only: события никогда не удаляются и не редактируются. Каждое новое сообщение из любого источника либо становится одним или несколькими событиями, либо игнорируется как шум.

### Структура события

Полная структура описана в разделе [Sync Session](#sync-session--пакет-изменений). Ключевые поля:

| Поле | Описание |
|---|---|
| `id` | Уникальный идентификатор события |
| `sync_session_id` | Сессия, в рамках которой извлечено событие (`null` для событий из чата) |
| `type` | Тип события (см. таблицу ниже) |
| `timestamp` | Время исходного сообщения/действия |
| `source_type` | `jira`, `slack`, `github`, `chat`, `user` |
| `source_id` | ID исходного элемента (тикет, сообщение, PR) |
| `author` | Автор исходного сообщения |
| `summary` | Краткое описание (1–2 предложения, формирует агент) |
| `raw_reference` | Оригинальный текст или ссылка на источник |

### Типы событий

| Тип | Когда создаётся |
|---|---|
| `requirement_stated` | Официальное требование зафиксировано (Jira-тикет, формальный документ) |
| `requirement_confirmed` | Неформальное требование подтверждено авторизованным лицом |
| `requirement_rejected` | Требование явно отменено |
| `open_question_raised` | Агент или участник команды поднял вопрос, требующий уточнения |
| `open_question_answered` | Пользователь ответил на открытый вопрос в чате |
| `decision_made` | Принято техническое или бизнес-решение |
| `blocker_identified` | Обнаружен блокер или проблема |
| `blocker_resolved` | Блокер устранён |
| `work_completed` | Задача или шаг завершены (слияние PR, закрытие тикета, подтверждение в переписке) |
| `status_update` | Общее обновление статуса |
| `current_step_override` | Пользователь скорректировал текущий шаг в чате |
| `user_note` | Пользователь добавил произвольный контекст в чате |

Все события из чата сохраняются через tool `update_consolidated` и немедленно учитываются при следующем анализе.

## Snapshot — состояние контекста

Snapshot — это одиночный документ, который строится агентом из event log во время анализа. Он состоит из трёх секций, хранящихся вместе как один документ.

При каждом запуске анализа snapshot перестраивается целиком на основе полного event log.

### Секция 1: Operational (операционная)

Отвечает на вопрос: **что происходит прямо сейчас?**

* Текущий шаг (current step) и его уверенность
* Текущий статус контекста: `not_started` / `in_progress` / `needs_attention` / `completed`
* Активные блокеры
* Открытые вопросы, ожидающие ответа (с указанием автора и ссылкой на источник)
* Кто что делает (если идентифицировано из переписки)
* Время последней значимой активности

### Секция 2: Narrative (нарративная)

Отвечает на вопрос: **как мы сюда попали?**

* История контекста: ключевые точки принятия решений
* Что было попробовано и не сработало
* Принятые решения и их обоснование
* Бизнес-сущности предметной области и их связи
* Важные ограничения и правила, выявленные из источников

### Секция 3: Engineering (техническая)

Отвечает на вопрос: **что именно нужно изменить в коде?**

* Технические сущности (сервисы, модели, API-эндпоинты, интерфейсы) с упоминанием источника
* **Relevant modules** — конкретные файлы и директории, идентифицированные следующим образом:
  1. Агент извлекает названия сущностей из event log (например, «PaymentService», «User model», «checkout endpoint»)
  2. Среди репозиториев, привязанных к контексту, агент ищет совпадения по описанию репозитория
  3. Если описания недостаточно — читает README репозитория для установления соответствия между доменными сущностями и файловой структурой
  4. Возвращает конкретные пути к файлам, если соответствие найдено, или директории верхнего уровня, если нет
* Активная ветка (branch) и ссылки на релевантные коммиты/PRs
* Известные проблемы: незаконченные реализации, технический долг, упомянутые баги
* Архитектурные ограничения (из переписки и документации)

## Handoff Packet — задача для агента-программиста

Handoff packet генерируется по требованию из engineering-секции snapshot. Он не хранится постоянно — формируется в момент копирования или экспорта.

Это финальный продукт агента: структурированный текст, который можно вставить в контекст Cursor или Claude Code и получить точный план реализации без дополнительных вопросов.

### Формат

```json
{
  "task_id": "PROJ-123",
  "title": "Краткое название задачи",
  "objective": "Одно предложение: что должно быть реализовано и зачем",
  "current_state": {
    "status": "not_started | in_progress | needs_attention | completed",
    "branch": "feature/branch-name (из привязанного репозитория)",
    "relevant_modules": [
      "src/services/payment.ts",
      "src/domain/order.ts",
      "src/api/checkout.ts"
    ]
  },
  "completed": [
    "Что уже сделано (из событий work_completed и requirement_confirmed)"
  ],
  "decisions": [
    {
      "decision": "Принятое решение",
      "why": "Обоснование (из событий decision_made)"
    }
  ],
  "constraints": [
    "Ограничения и правила, которые нельзя нарушать"
  ],
  "known_issues": [
    "Известные проблемы (из событий blocker_identified)"
  ],
  "next_steps": [
    "Конкретные шаги к реализации"
  ],
  "acceptance_criteria": [
    "Критерии, по которым можно считать задачу выполненной"
  ],
  "evidence": [
    "event-441",
    "event-442",
    "event-448"
  ]
}
```

Поле `evidence` содержит идентификаторы событий из event log, из которых сформирован этот packet. Это позволяет при необходимости проверить источник любого утверждения.

## Схема взаимодействия компонентов

```
  [Refresh All]
       │  создаёт sync_session_id
       ▼
Jira / Slack / GitHub / файлы
  (все элементы тегируются sess-id)
       │
       │          [Chat Input]
       │               │ user_note /
       │               │ open_question_answered /
       │               │ current_step_override
       │               │ (sync_session_id: null)
       │               │
       ▼               ▼
  [Analyze]  ←  берёт дельту от
               last_analyzed_session_id
       │
       ▼
 [ Event Extraction ]
 Каждое сообщение → каноническое
 событие с sync_session_id
       │
       ▼
  [ Event Store ]
 Append-only лог (все источники)
       │
       ▼
   [ Projection ]
 Строятся три секции snapshot:
 ┌──────────────────────────────┐
 │  Operational  │  Narrative   │
 │─────────────────────────────│
 │          Engineering         │
 │  (relevant_modules via       │
 │   repo README + description) │
 └──────────────────────────────┘
       │
       ▼ (по запросу / кнопка Export)
 [ Handoff Packet Generator ]
 Из engineering-секции собирается
 handoff packet для coding-agent'а
```
